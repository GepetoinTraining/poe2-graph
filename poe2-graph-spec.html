1. Thesis

Path of Exile 2 ships its build-construction game as a graph database. Passive tree, atlas tree, ascendancies, weapon-set specializations, and choice-resolution overrides all share one schema: nodes addressable by 16-bit hash, with a separate skill-override table for multi-choice resolution, encoded into save formats as flat coordinate sequences. The web URL encodes a player's traversal as binary. The in-game .build file encodes the same information as JSON, using stable string IDs.

This spec describes a Claude-native toolkit for that graph. The toolkit reads build URLs and .build files, answers planning questions through graph queries (shortest paths, stat aggregation, build comparison), and emits .build files the game ingests directly via its file watcher. The mechanical part of PoE 2 is downstream from the planning part; this toolkit makes Claude useful at the planning layer.

Spec v0.3 — convergence after Claude Code's first execution pass

v0.2 was pre-implementation. v0.3 captures what was actually built, what was deferred via community handoff, and what the implementation discovered the spec got wrong. Phase 1 and Phase 2 are shipped (parser, build_reader/writer, graph, resolvers, stats, allocation API, poe2db client, EXILE personalization layer, self-updater, filesystem scanner). 103 tests green. League start (PoE 2 0.5 Return of the Ancients) is Friday 2026-05-29.

Beyond the originally-scoped phases, v0.3 also documents the surfaces we built that weren't in v0.2 — the EXILE per-player profile system (§13), the self-update mechanism (§16), and the community-handoff pattern (§6a) that explicitly delegates parts of the surface (visualization, item filters, item rendering, market data) to license-clean community projects rather than reinventing them. Spec divergences discovered during build are catalogued in §15.

2. Architecture

Three layers in PoE 2, each with a different rate of change:

LayerMutates onReads fromImplementation
Save format player choice — web URL bytes or .build JSON
Stat sheet equip / allocate save + graph + items + skillOverrides flat hash table (game-internal)
Combat loop 60Hz stat sheet only source-blind dispatch (game-internal)

Our toolkit lives at layer 1. We never simulate combat. We parse save formats and walk the graph. Damage calculations are someone else's problem (and a worse problem to take on; Path of Building has been carrying that burden for a decade across community maintainers).

The architectural advantage

Every existing build tool re-implements GGG's resolution layer in Lua or JS. They break every patch. They scale O(rules × items × patches) in maintenance cost. We instead trust the canonical graph data GGG publishes and only do graph operations on it. Our maintenance scales O(1) per patch: refresh the JSON, ship.

This mirrors the game's own architecture. Sources collapse to stats at bind time, not combat time. We mirror that decision: meaning collapses to graph structure at query time, not analysis time. The combat loop doesn't care if +5 Intelligence came from a jewel, an item, a passive, or a skill override on an attribute node. Neither do we.

3. Byte format verified against test URL

The web format is documented by GGG as Version 7, current with Path of Exile 2: Return of the Ancients (0.5.0). Quoting the official spec:

HEADER (8 bytes)
  uint32   version          (always 7)
  uint8    class             (e.g. 7 = Sorceress)
  uint8    ascendancy        (e.g. 1 = Stormweaver)
  uint16   count of data (n) (number of allocation records)

RECORDS (variable length, n entries)
  uint16   node hash
  uint16   flags
  uint8?   weapon set        if (flags & 0b00000001) == true
  uint16?  skill override    if (flags & 0b00000010) == true

The base64url-encoded string after pathofexile2.com/game/passive-skill-tree/ decodes directly to this binary. Standard base64url-safe alphabet with padding stripped.

Record structure interpretation

Flags valueLengthMeaning
0x00004 bytesPlain allocation. Node is on both weapon sets. No multi-choice resolution.
0x00015 bytesWeapon-set-specific allocation. Active only on the named weapon set (0 or 1, possibly more).
0x00026 bytesMulti-choice node (Attribute, Mastery). The skill_override field points to a row in the skillOverrides table.
0x00037 bytesBoth: weapon-set-specific AND multi-choice (e.g. an Attribute node allocated only on weapon set 2).

Higher flag bits (0b00000100 and above) are reserved by the format. Pedro's test URL only exercises bits 0 and 1. Reserved bits likely cover features GGG hasn't shipped yet, or features in 0.5 we haven't yet seen in a build (Runeforging, Instilled emotions on items, etc.).

Verified parse: Pedro's test build

Total bytes: 687
Header: version=7, class=7 (Sorceress), ascendancy=1 (Stormweaver), n=142

Flag distribution:
  0x0000 (plain):              75 records  — main tree, shared across both sets
  0x0001 (weapon-set tag):     28 records  — split between set 1 (8) and set 2 (25)
                                            (3 jewel sockets cross the boundary)
  0x0002 (skill-override):     34 records  — Attribute choices, mostly Intelligence
  0x0003 (set + override):      5 records  — Attribute picks specific to weapon set 2

Total: 142 records, 687 bytes consumed. Round-trip clean.

Skill override resolution

The skill_override field is a uint16 pointing into data.skillOverrides in the published tree JSON. The override table has 83 entries (in 0.5). Most relevant for our parser:

skillOverrides[26297] = { name: "Strength",     grantedStrength:     5 }
skillOverrides[14927] = { name: "Dexterity",    grantedDexterity:    5 }
skillOverrides[57022] = { name: "Intelligence", grantedIntelligence: 5 }
skillOverrides[46793] = { name: "Damage",        stats: ["5% increased Damage"] }
skillOverrides[44242] = { name: "Defences",      stats: ["5% increased Armour, Evasion and Energy Shield"] }
... 78 more

When the parser encounters a node with flags & 0b00000010, the trailing uint16 names the choice. The Attribute node itself has no stats; its stats come from the overrides table at resolution time. This is the central-noded lookup pattern made concrete: nodes are coordinates, overrides are choices, both resolve to flat (stat_id, value) tuples at bind time.

The clean separation

This format design means: a node's identity (where it sits on the tree) is independent of what it grants (which choice was made). A jewel that grants "+5 Int" produces the same combat-layer effect as an Attribute node with skill_override=57022. The save format records the choice, not the effect. The game resolves the choice into the effect at bind time. The combat loop reads only the resolved effect. Three layers, three rates of change, one stat table.

Reference parser (Python)

import struct, base64

def parse_build_url(url_or_code):
    # accept either full URL or just the encoded portion
    code = url_or_code.rsplit('/', 1)[-1] if '/' in url_or_code else url_or_code
    code += '=' * ((4 - len(code) % 4) % 4)
    raw = base64.urlsafe_b64decode(code)

    version = struct.unpack('>I', raw[0:4])[0]
    assert version == 7, f"Only v7 supported, got v{version}"
    cls         = raw[4]
    ascendancy  = raw[5]
    n_records   = struct.unpack('>H', raw[6:8])[0]

    i = 8
    records = []
    for _ in range(n_records):
        node_hash = struct.unpack('>H', raw[i:i+2])[0]
        flags     = struct.unpack('>H', raw[i+2:i+4])[0]
        i += 4
        weapon_set, skill_override = None, None
        if flags & 0b00000001:
            weapon_set = raw[i]; i += 1
        if flags & 0b00000010:
            skill_override = struct.unpack('>H', raw[i:i+2])[0]; i += 2
        records.append({
            'node_hash': node_hash, 'flags': flags,
            'weapon_set': weapon_set, 'skill_override': skill_override
        })

    return {
        'version': version, 'class': cls, 'ascendancy': ascendancy,
        'records': records
    }

Tested against Pedro's URL: 142 records, final byte offset matches total length exactly, all node_hashes resolve to entries in data.nodes, all skill_override values resolve to entries in data.skillOverrides. The reference implementation is the entire parser. Round-trip and re-encode is a symmetric operation; we have not yet written the encoder but the format is fully specified.

4. Graph model

GGG's official passive tree export ships as a 5MB JSON with this structure:

{
  "tree": "Default",
  "classes":         [ ... 12 entries with class start nodes + ascendancy subtrees ... ],
  "groups":          { ... 1572 orbital clusters (visual layout) ... },
  "nodes":           { ... 5102 nodes ... },
  "edges":           [ ... 6021 {from, to} records, addressable by index ... ],
  "skillOverrides":  { ... 83 choice-resolution entries ... },
  "jewelSlots":      [ ... node ids of all jewel sockets ... ],
  "min_x" / "min_y" / "max_x" / "max_y": world bounds for visual rendering
}

Each node carries:

{
  "id": "intelligence11",          // string id used by .build format
  "skill": 22419,                  // numeric id used by web URL (node_hash)
  "name": "Attribute",
  "stats": ["+5 to any [Attributes|Attribute]"],
  "isNotable": false,
  "isKeystone": false,
  "isJewelSocket": false,
  "isMastery": false,
  "isMultipleChoice": false,
  "isMultipleChoiceOption": false,
  "isGenericAttribute": true,      // → expect a skill_override on allocation
  "ascendancyId": null,            // or "Sorceress1", "Druid2", etc.
  "group": 748,
  "orbit": 0, "orbitIndex": 0,
  "x": -478.005, "y": -2158.22,
  "out": ["18407", "4739"],        // neighbor node ids (strings, decimal)
  "in": [],
  "edges": [2942, 2943]            // indices into top-level edges array
}

Edges are first-class addressable objects with their own indices, not just adjacency-list entries. This is a graph database schema, not just a graph. Future patches can attach modifiers to edges (mastery effects, path-conditional bonuses) without changing the save format, because the save format records only node visits.

Canonical queries

Once loaded into NetworkX, every interesting build question becomes a single graph operation:

QuestionGraph operation
Distance from class start to keystone X?nx.shortest_path_length(G, start, X)
Optimal route through N notables?Steiner tree approximation
Which allocated nodes are orphaned from start?connected component check on allocated set ∪ start
Nearest unallocated notable?BFS from allocated frontier until notable hit
Build A vs Build B diff?set difference on allocations + path comparison
Stat aggregation for build?sum node.stats + skillOverrides[so].stats across allocated set

The stat aggregation step requires a stat parser (turning "15% increased Critical Hit Chance for Spells" into a structured tuple). This is the only place we re-implement game rules. We do it minimally: parse string → tuple, no math, no damage simulation. Aggregating identical stat_ids across sources is simple addition.

Path length sanity check

From Witch start (node 54447) to Ancestral Bond (node 45202): 17 graph hops. Confirmed via nx.shortest_path on the loaded graph. This is what makes dual-spec characters (like Pedro's) compelling — the 17 points only need to be allocated on one weapon set, not shared across both.

5. The .build file format

Officially documented at pathofexile.com/developer/docs/game. JSON file dropped into Documents/My Games/Path of Exile 2/BuildPlanner/. The game's file watcher detects it and renders inline guidance: passive routing in the tree, gem recommendations during crafting, gear hints on inventory slots.

{
  "name":         "Crit-Freeze Spark Stormweaver",
  "author":       "claude + pedro",
  "description":  "Cold-conversion Spark via Call of the Brotherhood",
  "ascendancy":   "Sorceress1",

  "passives": [
    "intelligence11",                       // bare string = just allocate
    "lightning_damage4",
    { "id": "intelligence45",
      "additional_text": "{{Pick after Crit Overload}}",
      "level_interval": [55, 65],
      "weapon_set": 1 },                    // optional weapon-set targeting
    ...
  ],

  "skills": [
    { "id": "Metadata/Items/Gems/SkillGemSpark",
      "support_skills": [
        "Metadata/Items/Gems/SupportGemControlledDestruction",
        { "id": "Metadata/Items/Gems/SupportGemInevitableCritical",
          "additional_text": "{After level 30}}" }
      ] }
  ],

  "inventory_slots": [
    { "inventory_id": "Weapon1",
      "additional_text": "{Wand}\n{+Lightning Spell Skills priority}" }
  ]
}

The two-id reality

Each passive node has two identifiers in the published tree JSON:

  • skill: numeric, used by the web URL binary format (the node_hash field above)
  • id: string, used by the .build JSON format (e.g. intelligence11, melee17, strength89)

Our code joins these via the tree JSON's nodes dict. The web URL parser produces numeric IDs; the .build writer needs string IDs; the resolver maps both to display names and stats. String IDs are probably more stable across patches than numeric ones, since renaming a node would break in-game guidance for existing players. The .build writer should prefer string IDs wherever possible.

Markup format

The additional_text field supports rich markup the game renders inline:

TypeKeys
Font weight/style<r> regular, <b> bold, <i> italic, <u> underline
Font size<s> small, <m> medium, <l> large
Colour<red>, <orange>, <yellow>, <green>, <blue>, <indigo>, <violet>, <black>, <white>, <grey>, <bronze>, <silver>, <gold>, plus <rgb(r,g,b)>
Wrapping{Example Text} — the curly braces are mandatory, the tag without braces does nothing

Markup nests: <m>{<red>{Strength +5 is recommended}} = medium font, red text.

This is the league-start deliverable

0.5 launches Friday May 29. The .build format launched three weeks ago. Almost nobody is using it yet — Mobalytics and YouTube guides still dominate. A skill that auto-generates rich .build files from a player's situation, with markup-annotated routing decisions, is something nobody has built because the format is days old. The whole point of the league-start scope is to ship something that lets Claude be the player's planning partner during their first hours in the new league, with guidance rendered inline by the actual game client.

6. Scope phases

Phase 1: Read & summarize shipped

  • Parse web URL via the v7 byte format — parser.py, round-trip exact against test corpus
  • Parse .build JSON files — build_reader.py, validated against GGG's reference Titan Warrior example
  • Load tree JSON, build NetworkX graph — resolvers.py + graph.py, 5101 nodes / 6015 edges
  • Resolve allocations: notables, keystones, jewel sockets, ascendancy nodes — graph.summarize
  • Resolve skill_overrides via the choice table — resolvers.Tree.override*
  • Detect dual-spec characters — weapon_set_split in summary
  • Answer graph questions — shortest paths, orphans, nearest unallocated notables, Steiner-tree multi-target routing
  • Added: mutable Allocation API (allocation.py) — mid-conversation build construction, not just reading

Phase 2: Write .build files shipped

Reverse direction. Claude takes a player's situation (current tree, goals, league context, current level) and emits a .build file with annotated routing. Player drops it in their BuildPlanner/ folder. Game renders the guidance inline.

  • Convert numeric ↔ string IDs via tree JSON join — resolvers
  • Generate additional_text annotations with markup — build_writer.red/bold/medium/...
  • Support weapon_set targeting for dual-spec recommendations
  • Support level_interval for progression guidance (scalar form OR [start, end] pair)
  • Validate against schema — build_writer.validate
  • Added during build (from natwarth's parser): unique, hint fields on inventory slots; level_interval on supports
  • Companion item filter: handoff → NeverSink (see §6a). Filter generation is deferred to the canonical community filter; we recommend strictness and personalization notes, we don't reinvent.

Phase 3: Artifact workbench deferred via handoff

Original v0.2 plan: HTML/JS artifact that loads tree JSON from IndexedDB, renders structured analysis. v0.3 update: natwarth/poe2-skilltree (MIT-pending) already does this beautifully. We hand off via URL — Allocation.to_url() produces canonical v7 URLs that paste directly into the hosted viewer. The forthcoming WebSocket messenger (messenger.py, license-blocked) will turn this from one-way handoff into bidirectional live editing.

Phase 4: Connector with OAuth later · application-blocked

MCP server registered with GGG. Reads the player's account profile, characters, current passive allocation. Generates personalized .build files from live character state. Reads currency exchange rates for craft-cost analysis. Requires a formal application to GGG that Pedro writes, in Pedro's voice, justifying scopes individually.

GGG OAuth registration policy

From the developer docs: "Due to the large volume of recent requests, we will immediately reject any low-effort or LLM-generated requests. We expect you to read and understand these docs, and to have a clear vision for what you want to do before requesting OAuth access." The application is itself the deliverable for this phase, not the code. Written by Pedro. Pedro's 2012 backer history is a positive signal but not a guarantee.

Phase 5: Live workbench later · composes 3+4

Connector + artifact + Claude in conversation = the live workbench. Player asks "what should I craft tonight?", Claude reads their character, knows the league economy, looks at their goal, suggests a craft path with currency cost estimates. This is the "playing the game with players" outcome.

Bounded by what GGG exposes for PoE 2: account profile, characters, currency exchange, item filters. No stash API for PoE 2 yet (only PoE 1 has stash endpoints). The live workbench is bounded by GGG's PoE 2 endpoint roadmap.

poe2db's role, clarified

poe2db.tw runs a data extraction pipeline against the game files (probably using LibGGPK or similar) and serves the result through a CDN with URLs keyed by the game's internal Metadata\ paths. Their cdn.poe2db.tw/cache2/us/ endpoint serves cached HTML popups for any item by path. This is the canonical source for resolving .build skill IDs like Metadata/Items/Gems/SkillGemSpark into actual gem stats, since GGG's official Data Exports page says "We are currently unable to provide any PoE2-specific data" beyond the tree JSONs.

The heap snapshot investigation showed that poe2db's page-level heap is mostly ad infrastructure; the data is server-side, served on demand. The right way to use poe2db is as a parameterized lookup, not by scraping rendered pages.

Existing MCP server we should not duplicate

sergeyklay/poe2-mcp-server already exists. Tools: poe2_currency_prices, poe2_item_price, poe2_exchange_top, poe2_wiki_search, poe2_db_lookup, poe2_meta_builds. No OAuth required. Built on poe.ninja + poe2db + poe2wiki. The phase 4+ connector we build should be the OAuth complement (personal character data, item filter R/W), not a replacement.

9. Artifact layer

The artifact is what a player sees in a Claude conversation. It loads the cached tree JSON from IndexedDB (5MB fetched once, persists across reloads within the artifact origin). Subsequent interactions are instant.

Artifact responsibilities

  • Accept paste-in web URL or .build upload
  • Parse and resolve via the same logic the skill uses
  • Render: structured allocation summary, notable list, keystone highlights, stat aggregation table, dual-spec breakdown
  • Render: graph queries on demand ("path to X", "notables I'm 2 nodes from")
  • Export: download .build file with annotations
  • Compare: diff two builds (allocation set difference, stat delta, ascendancy difference)

What the artifact must not do

  • Simulate combat or compute DPS — out of scope, hard to maintain, PoB exists
  • Store player accounts or auth tokens — no OAuth at the artifact level
  • Talk to the GGG API directly — rate limits live at the connector/MCP layer

13. EXILE — the player profile system shipped, added in v0.3

Not in v0.2. Emerged from the design conversation about what makes Claude useful at the floor-lowering scope: generic advice is mediocre advice, and the path to non-generic is per-player context that persists across conversations. CLAUDE.md gives project context; EXILE.md gives player-in-this-league context.

Three-rate-of-change discipline

Same architectural move as §2's "three rates of change":

  • PLAYER.md — durable, years. Identity, knowledge surface, playstyle preferences, capacity signals (grind, crafting engagement, peak wealth tier, systems knowledge).
  • LEAGUE_<id>.md — per league, months. Goal, time budget, mechanics engaged, session log.
  • CHARACTER_<slug>.md — per playthrough, days/weeks. Class, ascendancy, current level, build URL + companion .build file, archetype/defense/offense tags, milestones.

The three compose into ~/.claude/projects/<project-id>/EXILE.xml — an auto-loaded structured index Claude reads on every session. The XML is rebuilt artifact (never hand-edited); the .md files are the editable surface.

Tag confidence math

Every tag carries a confidence in [0, 1) where 1.0 is unreachable. Asymptotic Bayesian updates:

positive delta: new = old + (1 - old) * delta
negative delta: new = old + old * delta  (delta < 0)

bump_confidence(0.0, 0.5) == 0.5
bump_confidence(0.5, 0.5) == 0.75
bump_confidence(0.75, 0.5) == 0.875
bump_confidence(0.875, 0.5) == 0.9375
... approaches 1.0 but never reaches it

Calibration table (initial confidences after onboarding evidence):

Evidence typeInitial confidence
Filesystem tool present0.95
Single-character archetype0.40
Two characters confirming same archetype0.65
Three+ characters same archetype0.85
Player explicitly confirms in questionnaire0.85
Player explicitly deniesbump current by −0.5
Inferred from item modifiers alone0.30

Dual-game support

Most players play both PoE 1 and PoE 2. The system treats them as separate-but-related dimensions:

  • Game-agnostic tags (HC tendency, trade preference, time budget) at the section root
  • Game-specific tags nest by game: knows.poe1.essence_crafting, knows.poe2.spirit_management
  • Active/dormant character status is exclusive per game — one PoE 1 character and one PoE 2 character can both be active simultaneously

The four-phase onboarding flow

Detailed in ONBOARDING.md. Triggered when EXILE/DONE is absent. Once complete, subsequent sessions skip directly to session-start hooks.

  1. Filesystem scan — passive, ~5s. Detect installed PoB / Awakened PoE Trade / Exilence / ChaosRecipeEnhancer / game installs / custom filters. Compresses the questionnaire by eliminating questions whose answers are already evident from disk.
  2. Tailored questionnaire — HTML form artifact. Hard constraints (HC/SC, trade/SSF, time budget, goal), PoE history, trigger questions derived from what the scan found.
  3. Artifact requests — player drops in: account profile screenshot, Standard currency stash (scan for chase categoricals first — Mirror, Mageblood — then quantities), 1 best-equipped character, 1-2 varied characters, atlas tree. Claude extracts structured tags from each.
  4. Synthesize — assemble PLAYER.md draft, player reviews, snapshot to PLAYER.initial.md, write EXILE/DONE, regenerate EXILE.xml.

Re-onboarding triggers: new league starts (new LEAGUE_<id>.md), new character starts, or player explicitly requests "update my profile."

14. Divergences discovered during build v0.3

Implementation surfaced six places where the v0.2 spec was wrong or under-specified. All caught by tests against real data; all corrected in code; all recorded in agent memory so they don't have to be re-derived.

v0.2 saidRealitySurface affected
Atlas tree shares schema with passive tree (§2/§4) Atlas nodes have no id, no edges array; only out/in adjacency. isWormhole, reminderText, flavourText are atlas-only fields. grantedSkill and ascendancyId are passive-tree-only. graph.build_graph handles both via tree.raw.get("edges") fallback to adjacency walk; resolvers doesn't reuse types across trees.
cdn.poe2db.tw/cache2/ is the data CDN (§7) No data CDN. cdn.poe2db.tw serves only static assets (CSS/JS/images); all data paths return 403. The actual delivery: HTML page with the full structured JSON embedded inline as new ModsView({...}). One HTTP GET → regex-extract → json.loads. poe2db_client.py uses the inline-JSON path.
Weapon set byte = 0 or 1 (§3) Actually 1 and 2 (1-indexed). Pedro's verified build shows {1: 8, 2: 25} distribution — no zeros. Higher values likely reserved for future GGG features. parser.py, allocation.py, graph.summarize.weapon_set_split. Validator no longer rejects values ≥ 2.
Ascendancies are strings in tree.classes[i].ascendancies They're dicts with name + flavourText + layout fields. Some slots are literal None for unreleased ascendancies (Ranger's middle slot is observed empty). resolvers.Tree.ascendancy_name reads .name from the dict.
Class start nodes carry single classStartIndex (implied) It's an array — paired classes share start positions. PoE 2's three new classes reuse PoE 1's six wheel-starts: Marauder/Warrior (47175), Witch/Sorceress (54447), Ranger/Huntress (50459), Duelist/Mercenary (50986), Shadow/Monk (44683), Templar/Druid (61525). graph.class_start_node scans the array.
The tree.nodes dict is keyed by string id (implied by §4 schema) Dict is keyed by stringified skill hash (e.g. "42761"); the string id lives inside the node as node.id. A structural "root" entry has neither skill nor id. Net: 5102 dict entries, 5101 real nodes. resolvers.Tree exposes three indexes: nodes_by_dict_key (raw), nodes_by_string_id (re-keyed by node.id), nodes_by_skill_hash (re-keyed by node.skill).
The passive tree is one connected component (implied by §4 query playbook) It's not. Each ascendancy is its own subgraph. nx.is_connected(g) returns False. Steiner tree and shortest-path code must handle this — restrict to the component containing the relevant terminal or class start. graph.steiner_route restricts to the largest component containing the first terminal.
Class start nodes are records in the build (implied) They're implicit. The class field in the byte header determines start position; the start node is NOT in the records array. "Witch start → Ancestral Bond = 17 hops" means 17 new allocations on top of the implicit start. Allocation.cost_to and Allocation.extend_to exclude implicit start nodes from cost/allocation counts.
.build inventory slots have only inventory_id + additional_text (§5) Per natwarth's parser (and confirmed against GGG's docs), slots also accept unique (recommended unique item name) and hint (short inline hint). Supports also accept level_interval. And level_interval can be a single int (start level only), not just a [start, end] pair. build_reader.py + build_writer.py.

Naming and badging

GGG requires every public/widely-available application to display: "This product isn't affiliated with or endorsed by Grinding Gear Games in any way." The artifact, the MCP server, and any user-facing surface must carry this. Skill-level work doesn't need it; player-facing artifact output does.

User-Agent format for OAuth API calls: OAuth {clientId}/{version} (contact: {contact}) — applies once we're in OAuth land. Public APIs (poe.ninja, poe2db, wiki) need an identifiable User-Agent too; we should set one per skill convention.

Content creator integration

The .build file format has an author field. Build creators (AnimePrincess, Allie, Mathil, etc.) will naturally start publishing .build files alongside their videos as the format catches on. Two integration paths to keep in mind:

  1. Read other creators' .build files — phase 1 already does this. A player downloads AnimePrincess's Stormweaver leaguestarter and asks Claude "what does this do and where am I in it".
  2. Generate .build files from creator video transcripts or build pages — phase 3+. Claude reads a Mobalytics page, generates a .build file capturing the recommended routing. Quality-of-life multiplier for the whole ecosystem.

Creator-credit conventions: when generating a .build from a third-party guide, the author field should credit the original creator with a note that the file is auto-generated. Annotation text should link back to the source.
